What is VeloArch?
VeloArch estimates how fast and how efficiently an AI model runs on a target chip — using math, not real hardware. Every number shown comes from a formula. This page explains every term in plain language.
Your AI Model — What We Measure
FLOPs — Floating-Point Operations
ops  or  GFLOPs (billions)
Every multiply or add on a decimal number is one FLOP. A convolution layer does millions of them — we count the total across the whole network to know how much arithmetic work the model requires.
Conv2d: ops = 2 × B × H_out × W_out × C_in × C_out × Kh × Kw
Linear: ops = 2 × B × in_features × out_features
The ×2 counts both the multiply AND the add in each MAC (IEEE standard).
ResNet-18 on 224×224 ≈ 3.6 GFLOPs. A GPT-2 medium forward pass ≈ 500 GFLOPs.
MACs — Multiply-Accumulate Operations
1 MAC = 2 FLOPs
A MAC is one multiply plus one add — the basic operation of neural network math. Many papers quote model size in GMACs; just multiply by 2 to get GFLOPs.
1 MAC = 1 multiply + 1 add = 2 FLOPs
Memory Traffic
MB (megabytes moved per inference)
The processor must load data from RAM before it can work on it. Memory traffic counts the bytes moved: layer weights (learned parameters) and output activations (numbers each layer produces). Heavy memory traffic is the primary cause of the memory bottleneck.
mem per layer = (weight parameters + output elements) × 4 bytes (float32)
Input Shape — B × C × H × W
Batch × Channels × Height × Width
B = batch size (images processed at once; use 1 for single-image latency). C = colour channels (3 for RGB). H × W = resolution. Larger images → more FLOPs and more memory → higher latency.
Classification: 224×224. Object detection (YOLO): 320×320 or 640×640.
Arithmetic Intensity (AI)
ops/byte — the most important model characteristic
How much arithmetic the model does per byte it moves. High AI = compute-heavy relative to memory. Low AI = memory-hungry relative to compute. This single number determines which hardware resource will be the bottleneck.
AI = ops / memory_bytes
ResNet-18 AI ≈ 64 ops/byte — quite compute-dense. A shallow embedding lookup might be 1–4 ops/byte.
Hardware Parameters — What You Configure
Parallel Units
count — processing elements active each clock cycle
The number of arithmetic units working simultaneously each clock tick — the width of the compute pipeline. More units = more work per second. For embedded VPUs this is the MAC array width. For GPUs, set it to CUDA cores × 2 (each core does 2 ops/cycle via FMA).
VPU: 256 units × 1 GHz = 256 GOPS
GTX 1060: 1280 cores × 2 (FMA) × 1.708 GHz = 4.375 TFLOPS
Frequency (Clock Speed)
Hz  (GHz = billions of cycles/s)
How many clock cycles the chip completes each second. Each cycle, all parallel units finish one operation. Doubling frequency doubles compute speed — but also raises power consumption.
Memory Bandwidth
GB/s — the pipe width between memory and processor
The maximum rate at which data can flow from DRAM to the chip. If the chip is ready to compute but waiting for data, it stalls — bandwidth is the bottleneck.
LPDDR4 (phones) ≈ 50 GB/s · GDDR5 (GTX 1060) = 192 GB/s · GDDR7 (modern GPU) = 448 GB/s.
Energy per Operation (E/op)
pJ/op — picojoules per floating-point operation
How much electrical energy one arithmetic operation costs. Depends on the chip's process node (smaller = cheaper), voltage, and design. Derived from TDP ÷ peak throughput.
E/op = TDP [W] / peak_compute [ops/s]
GTX 1060: 120 W / 4.375×10¹² = 27.4 pJ/op
NPU (systolic array): 1 pJ/op — far more efficient
Energy per Byte (E/byte)
pJ/byte — picojoules per byte transferred from memory
How much energy moving one byte of data costs. Memory accesses are surprisingly expensive — often the dominant energy cost in memory-bound workloads.
LPDDR4 (VPU): 5 pJ/byte · LPDDR5 (NPU): 3 pJ/byte
GDDR5 (GTX 1060): 35 pJ/byte · GDDR7: 20 pJ/byte
Derived Hardware Properties — Calculated Automatically
Peak Compute
GOPS or TFLOPS — the ceiling on arithmetic speed
The absolute maximum operations per second the hardware can execute, assuming every unit is busy every cycle. No workload can exceed this number.
peak_compute = parallel_units × frequency
Ridge Point
ops/byte — the roofline knee, where bottleneck switches
The arithmetic intensity value at which performance transitions from memory-limited to compute-limited. Workloads with AI above the ridge point are compute-bound; below it they are memory-bound.
ridge_point = peak_compute / memory_bandwidth
VPU: 256 GOPS / 50 GB/s = 5.1 ops/byte
GTX 1060: 4.37 TOPS / 192 GB/s = 22.8 ops/byte
Output Metrics — What VeloArch Reports
Latency
ms per inference — how long one forward pass takes
Whichever resource (compute or memory) takes longer determines the total time. Latency is the maximum of the two — the bottleneck sets the pace.
compute_time = ops / peak_compute
memory_time = memory_bytes / bandwidth
latency = max(compute_time, memory_time)
This is a theoretical lower bound. Real GPU latency for batch=1 is typically 5–10× higher due to kernel launch overhead and low occupancy. Embedded accelerators are closer to this estimate.
Energy
mJ per inference — total electrical energy consumed
Two independent cost centres: arithmetic energy and memory-transfer energy. In memory-bound workloads the memory term dominates; in compute-bound workloads the arithmetic term dominates.
energy = ops × E/op  +  memory_bytes × E/byte
Embedded AI targets <1 mJ per inference. GTX 1060 uses ~100 mJ for ResNet-18 — optimised for performance, not efficiency.
Effective Throughput
GOPS — actual operations per second achieved by this workload
Unlike peak compute (a fixed hardware ceiling), effective throughput depends on both the model and the hardware. Compute-bound workloads approach peak compute; memory-bound workloads fall short because compute units idle while waiting for data.
eff_throughput = ops / latency
Memory-bound → eff_throughput = AI × bandwidth < peak_compute
Bottleneck
compute  or  memory
Compute-bound: the arithmetic units are the constraint — the memory bus delivers data fast enough but the chip can't crunch faster.
Memory-bound: the memory bus is the constraint — compute units sit idle waiting for data.
bottleneck = "compute" if AI ≥ ridge_point
bottleneck = "memory" if AI < ridge_point
Bound Ratio (×N)
dimensionless — how far from the ridge point
×12 compute means the model's AI is 12× above the ridge point — very deeply compute-bound. ×0.2 memory means the AI is only 20% of the ridge point — very deeply memory-bound. Closest to ×1.0 means most balanced for that hardware.
bound_ratio = AI / ridge_point
HW Utilization
% of peak compute the workload can actually exploit
Compute-bound workloads hit 100% — every unit is busy. Memory-bound workloads fall below 100% — some units idle waiting for data. The best single number for asking "does this hardware fit this model?"
attainable = min(peak_compute, AI × bandwidth)
hw_utilization = attainable / peak_compute
Memory-bound: utilization = AI / ridge_point × 100%
If two architectures give the same latency, pick the one with lower HW utilization — it has more headroom for larger models.
Core Concepts
The Roofline Model
Williams, Waterman & Patterson, 2009
A two-line graph: x-axis = arithmetic intensity, y-axis = attainable performance. A sloped line on the left (memory-bound, slope = bandwidth) meets a flat ceiling on the right (compute-bound, ceiling = peak compute). The junction is the ridge point. VeloArch places every workload on this diagram and reads off latency, energy, and utilization analytically.
DVFS — Dynamic Voltage & Frequency Scaling
A power-saving technique used in phones, edge chips, and embedded AI
DVFS lowers the clock frequency and supply voltage when full performance is not needed. Because CMOS power is proportional to V² × f, and with DVFS voltage tracks frequency, energy per operation drops as the square of the frequency ratio — not linearly.
CMOS power: P = α × C × V² × f; with V ∝ f → E/op ∝ f²
VPU+DVFS at 0.7×: E/op = 2.0 × 0.7² = 0.98 pJ (not 1.4 — linear is wrong)
Why "Analytical" and Not Measured?
VeloArch uses closed-form formulas instead of running the model on real hardware. This lets you evaluate a model on hardware you don't own (e.g. a VPU still in design), compare dozens of configurations instantly, and reason about tradeoffs at design time.

The trade-off: the model assumes ideal conditions. Real-world latency for small batches on discrete GPUs is typically 5–10× higher due to kernel launch overhead and low occupancy. For dedicated embedded accelerators with fixed pipelines, the estimates are much closer to reality.
