What is VeloArch?
VeloArch lets you take any AI model and ask: "how fast would this run on hardware X, and how much energy would it consume?" It uses an analytical model — meaning it calculates estimates from first principles using math, without ever running the model on real hardware. Every number shown comes from a formula. This page explains every term you'll encounter, in plain language.
Your AI Model — What We Measure
FLOPs — Floating-Point Operations
Unit: ops  (or GFLOPs = billions of ops)
Every time a neural network does a multiplication or an addition on a decimal number, that is one floating-point operation. A convolution layer does millions of multiplications and additions — so we count the total across the whole network. This tells us how much arithmetic work the model requires.
Conv2d: ops = 2 × B × H_out × W_out × C_in × C_out × Kh × Kw
Linear: ops = 2 × B × in_features × out_features

The ×2 counts both the multiply AND the add in each multiply-add (IEEE standard).
ResNet-18 on a 224×224 image ≈ 3.6 GFLOPs. A transformer like GPT-2 medium is ~500 GFLOPs per token.
MACs — Multiply-Accumulate Operations
Unit: MACs  (1 MAC = 2 FLOPs)
A MAC is the basic building block of neural network math: multiply two numbers, then add the result to a running total. Because that is two operations (one multiply + one add), 1 MAC = 2 FLOPs. You will often see model sizes quoted in GMACs online — just double it to get GFLOPs.
1 MAC = 1 multiply + 1 add = 2 FLOPs
Memory Traffic
Unit: MB  (megabytes moved between memory and processor)
The processor cannot do arithmetic on data that is still sitting in RAM — it must be loaded first. Memory traffic counts how many bytes are moved: the layer weights (the learned parameters) and the output activations (the numbers produced by each layer). Heavy memory traffic slows things down when the memory bus is the bottleneck.
mem per layer = (weight parameters + output elements) × 4 bytes (float32)
Input Shape — B × C × H × W
Batch × Channels × Height × Width
This describes the shape of the data fed into the network for one forward pass. B is the batch size (how many images at once; usually 1 for latency measurement). C is the number of colour channels (3 for RGB images). H × W is the image resolution. Larger images produce more FLOPs and more memory traffic, so latency scales with resolution.
Classification uses 224×224, YOLO detection uses 320×320 or 640×640.
Arithmetic Intensity (AI)
Unit: ops/byte
Arithmetic intensity is the ratio of how much work the model does to how much data it moves. A high AI means the model is compute-heavy relative to its memory needs. A low AI means the model is memory-hungry — it moves lots of data for relatively little arithmetic. This is the most important single number for predicting where the bottleneck will be.
AI = ops / memory_bytes  [ops per byte transferred]
ResNet-18 AI ≈ 64 ops/byte — quite compute-dense. A simple embedding lookup might be 1–4 ops/byte.
Hardware Parameters — What You Configure
Parallel Units
Unit: count (no unit)
The number of arithmetic units that work simultaneously every clock tick. Think of it as the width of the assembly line: more units = more work done per second. In embedded VPUs this is the width of the MAC array (e.g. 256). In GPUs, this is the number of CUDA cores multiplied by 2 to account for FMA (Fused Multiply-Add, which does 2 ops per cycle per core).
VPU example: 256 MAC units × 1 GHz = 256 GOPS peak compute
GTX 1060: 1280 CUDA cores × 2 (FMA) × 1.708 GHz = 4.375 TFLOPS
Frequency (Clock Speed)
Unit: Hz  (GHz = billions of cycles per second)
The number of clock cycles the processor completes each second. One cycle is the smallest unit of time in a digital chip. Each cycle, all parallel units complete one operation. Doubling the frequency doubles the compute speed — but also increases power consumption.
cycles per second = frequency  (e.g. 1 GHz = 1,000,000,000 cycles/s)
Memory Bandwidth
Unit: GB/s  (gigabytes per second)
The maximum rate at which data can be moved between the main memory (DRAM) and the processor. Think of it as the width of the pipe connecting memory to the chip. If the processor is ready to compute but is waiting for data from memory, it is stalled — and bandwidth is the bottleneck.
LPDDR4 (phones/embedded) ≈ 50 GB/s. GDDR5 (GTX 1060) = 192 GB/s. GDDR7 (modern GPUs) = 448+ GB/s.
Energy per Operation (E/op)
Unit: pJ/op  (picojoules per floating-point operation)
How much electrical energy one arithmetic operation consumes. This depends heavily on the manufacturing process node (smaller = cheaper per op), the voltage, and the micro-architecture. It is derived from the chip's thermal design power (TDP) divided by its peak throughput.
E/op = TDP [W] / peak_compute [ops/s]

GTX 1060: 120 W / 4.375×10¹² ops/s = 27.4 pJ/op
NPU (28 nm systolic): 1 pJ/op — far more efficient
Newer chips use smaller process nodes (e.g. 4 nm vs 16 nm) and have much lower E/op. DVFS reduces it quadratically: halving voltage cuts E/op by 4×.
Energy per Byte (E/byte)
Unit: pJ/byte  (picojoules per byte transferred)
How much energy it costs to move one byte of data from memory to the processor (or back). Memory accesses are surprisingly expensive — often more costly than the arithmetic itself in memory-bound workloads. Different memory technologies have very different E/byte figures.
LPDDR4 (embedded VPU): 5 pJ/byte
LPDDR5 (embedded NPU): 3 pJ/byte
GDDR5 (GTX 1060): 35 pJ/byte
GDDR7 (modern GPU): 20 pJ/byte
Derived Hardware Properties — Calculated Automatically
Peak Compute
Unit: GOPS or TFLOPS  (giga/tera operations per second)
The absolute maximum number of floating-point operations the hardware can perform per second, assuming every unit is busy every cycle. This is the ceiling on how fast arithmetic can run. No workload can exceed this, no matter how well optimised.
peak_compute = parallel_units × frequency

VPU: 256 × 1 GHz = 256 GOPS
GTX 1060: 2560 × 1.708 GHz = 4.37 TOPS
Ridge Point
Unit: ops/byte  (same unit as Arithmetic Intensity)
The ridge point is the knee of the roofline curve — the exact arithmetic intensity at which the bottleneck switches from memory to compute. If a workload's AI is above the ridge point, the compute units are fully busy (compute-bound). If the AI is below, the memory bus is the limiting factor (memory-bound).
ridge_point = peak_compute / memory_bandwidth

VPU: 256 GOPS / 50 GB/s = 5.1 ops/byte
GTX 1060: 4.37 TOPS / 192 GB/s = 22.8 ops/byte
NPU: 1.02 TOPS / 100 GB/s = 10.2 ops/byte
Output Metrics — What VeloArch Reports
Latency
Unit: ms  (milliseconds per inference)
How long it takes to process one input through the model from start to finish. The roofline model says the true bottleneck is whichever of the two resources (compute or memory) takes longer to satisfy — so latency is the maximum of the two times.
compute_time = ops / peak_compute
memory_time = memory_bytes / bandwidth
latency = max(compute_time, memory_time)
This is a theoretical lower bound. Real-world latency is typically 5–10× higher for small batches on a GPU due to kernel launch overhead and low occupancy. For embedded accelerators it is closer to this estimate.
Energy
Unit: mJ  (millijoules per inference)
The total electrical energy consumed to run one inference. It has two independent parts: the cost of doing all the arithmetic, and the cost of moving all the data from memory. In memory-bound workloads the memory term dominates; in compute-bound workloads the arithmetic term dominates.
energy = ops × E/op  +  memory_bytes × E/byte
Embedded AI targets <1 mJ per inference for always-on sensors. The GTX 1060 uses ~100 mJ for ResNet-18 — not designed for efficiency.
Effective Throughput
Unit: GOPS  (giga operations per second, workload-dependent)
The actual number of operations per second the model achieves on this hardware. Unlike peak compute (which is a fixed hardware property), effective throughput depends on both the model and the hardware. If the workload is compute-bound it approaches peak compute; if it is memory-bound it is limited to AI × bandwidth, which is less than peak.
eff_throughput = ops / latency

Compute-bound: eff_throughput ≈ peak_compute
Memory-bound: eff_throughput = AI × bandwidth < peak_compute
Bottleneck
compute  or  memory
Which physical resource limits performance for this particular workload on this particular hardware. Compute-bound means the arithmetic units are the bottleneck — the memory bus delivers data fast enough, but the chip cannot crunch numbers any faster. Memory-bound means the memory bus is the bottleneck — the compute units are sitting idle, waiting for data to arrive.
bottleneck = "compute" if AI ≥ ridge_point
bottleneck = "memory" if AI < ridge_point
To fix a memory-bound workload: increase bandwidth, or reformulate the model to do more arithmetic per byte (e.g. fuse kernels, use larger batch sizes).
Bound Ratio
Unit: ×N  (dimensionless multiplier)
A number that tells you how far the workload sits from the ridge point. A bound ratio of ×12 compute means the model's arithmetic intensity is 12× above the ridge point — very deeply compute-bound. A ratio of ×0.2 memory means the AI is only 20% of the ridge point — very deeply memory-bound. The closer to ×1.0, the more balanced the workload is for that hardware.
bound_ratio = AI / ridge_point

> 1.0 → compute-bound (ratio shows how many times over the ridge point)
< 1.0 → memory-bound (ratio shows fraction of ridge point reached)
HW Utilization
Unit: %  (percentage of peak compute actually used)
The fraction of the hardware's peak compute that the workload can actually exploit. A compute-bound workload reaches 100% — every compute unit is busy. A memory-bound workload reaches less than 100% — some compute units sit idle because data is not arriving fast enough. This is the single most useful number for asking "does this hardware fit this model?"
attainable = min(peak_compute, AI × bandwidth)
hw_utilization = attainable / peak_compute

Compute-bound → 100% utilization always
Memory-bound → utilization = AI / ridge_point × 100%
If two architectures have the same latency for a workload, choose the one with lower HW utilization — it has more headroom for future model growth.
Core Concepts
The Roofline Model
Williams, Waterman & Patterson, 2009
The roofline model is a simple visual framework for predicting how fast a workload will run on a piece of hardware. Imagine a plot where the x-axis is arithmetic intensity (ops/byte) and the y-axis is attainable performance (ops/s). The curve has two regimes: a sloped line on the left (memory-bound, limited by bandwidth) and a flat ceiling on the right (compute-bound, limited by peak compute). The ridge point is where the two lines meet.

VeloArch applies this model analytically — it computes where on the roofline your model sits for each hardware target, and derives latency, energy, and utilization directly from the formula.
DVFS — Dynamic Voltage and Frequency Scaling
A power-saving technique
DVFS allows a chip to reduce its clock frequency and supply voltage when full performance is not needed, in order to save energy. The key insight is that CMOS circuits consume power proportional to V² × f (voltage squared × frequency). When you lower frequency, you can also lower voltage proportionally — so energy per operation drops as the square of the frequency ratio, not linearly.
CMOS dynamic power: P = α × C × V² × f
With V ∝ f:  E/op = P/f = α × C × V² ∝ f²

VPU+DVFS at 0.7× freq: E/op = 2.0 × 0.7² = 0.98 pJ (not 1.4 — that would be linear and wrong)
DVFS is widely used in smartphones and edge AI chips to trade latency for battery life. The VPU+DVFS preset in VeloArch shows how much energy you save by running at 700 MHz instead of 1 GHz.
Conv2d — 2D Convolution Layer
The most FLOPs-heavy layer type in most vision models
A convolutional layer slides a small filter (kernel) over the input image, computing a dot product at each position. The output is a new feature map. The number of operations scales with the output spatial size, the number of input and output channels, and the kernel size. Most of the FLOPs in ResNet, VGG, and YOLO come from Conv2d layers.
ops = 2 × B × H_out × W_out × (C_in/groups) × C_out × Kh × Kw
(Kh, Kw = kernel height/width; groups=1 for standard conv)
Linear (Fully Connected) Layer
Matrix multiply — common in classifier heads and transformers
A linear layer multiplies the input vector by a weight matrix to produce an output vector. Every input value is multiplied with every weight connecting to each output neuron. This is equivalent to a matrix multiplication. Transformer attention and feed-forward blocks are mostly made of Linear layers.
ops = 2 × B × in_features × out_features
Why "Analytical" and Not Measured?
VeloArch computes all results from closed-form formulas rather than actually running the model on hardware. This means you can evaluate a model on hardware you do not own (e.g. a custom VPU still in design), compare dozens of architecture configurations instantly, and reason about tradeoffs at design time.

The trade-off is that the analytical model assumes ideal conditions — no kernel launch overhead, perfect memory access patterns, and full hardware utilisation. Real-world numbers are typically 2–10× higher in latency for small batch sizes on discrete GPUs, and closer to the model for dedicated embedded accelerators with fixed pipelines.
